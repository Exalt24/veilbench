# Decisions and what each one costs

Every number here is read from a file under [`test-runs/`](test-runs/) that a command in the README writes. The corpus is generated by code (`veilbench/corpus/`), so each statement says what it was measured against.

## 1. Five ways to change a value, and what each keeps

The same 1,200 generated support tickets (250 customers, 6 categories, 840 for training and 360 for testing) went through each technique with the ground truth spans, so the table isolates what the technique itself does. Source: [`test-runs/utility.json`](test-runs/utility.json), command `veilbench utility`.

| technique | what the downstream system sees | category classifier accuracy | distinct customers the join key still gives (true: 246) | when it fits |
|---|---|---|---|---|
| none (raw text) | everything | 0.775 | 246 | never for training data |
| redact | `[EMAIL]`, `[PERSON]` | 0.817 | 1 | the text is only read for meaning and nobody needs to tell customers apart |
| mask | `m****@example.com`, `+** *** *** 0142` | 0.808 | 241 | a person must see the shape of a value (a support agent confirming the last four digits) |
| pseudonymize | the same made-up stand-in for the same value | 0.786 | 246 | records must still join: a customer across tickets, a user across logs, a column across tables |
| anonymize (generalize) | `1980s`, `[ADDRESS in Cebu City]`, `[EMAIL]@example.com` | 0.814 | 6 | aggregate analysis where a coarser fact is enough |
| synthesize | a freshly generated value of the same type | 0.792 | 1,197 | test data and demos: realistic looking, linked to no one |

What the table says:

- The classifier does not get worse. The identifiers in these tickets are noise for a category prediction, so removing them did not hurt and redaction scored slightly above the raw text. That is a property of this task, not a general promise: a task that reads the identifiers (spotting repeat customers, say) is where the join key column matters.
- Redaction and generalization destroy the join key (1 and 6 distinct customers out of 246). Pseudonymization keeps it exactly (246). Masking keeps most of it (241) because the first letter and the domain collide for a few customers. Synthesis makes every ticket a new person (1,197), which is what unlinkability looks like from the side of someone who wanted the join.
- Pseudonymization is the only technique here whose output can be linked back by someone holding the key, and for names it needs a stored map, because the stand-ins are derived by keyed hashing and not by encryption. Digit identifiers use FF1 and can be decrypted by the key holder. That is the cost: a key and a map are now sensitive data too.
- Secrets (API keys, tokens, passwords) are removed by every technique. A pseudonym for a credential has no use and a masked prefix tells an attacker the vendor.

## 2. Detection: why a union is not the answer

The first merge stretched every span to the union of what the detectors found. It raised recall and wrecked precision: a model's sloppy boundary around an e-mail swallowed the rule's clean one, so a correct finding became a false positive. The merge now works by priority (rules, then the GLiNER PII model, then the statistical model, then spaCy, then the LLM). A weaker span is trimmed to the part nothing better already covered, and dropped if less than half of it is new. Recall comes from detectors finding different things, not from stretching boundaries. Source: [`veilbench/detect/base.py`](../veilbench/detect/base.py), pinned by `tests/test_rules_and_merge.py`.

The score that decides is F2, which weights recall four times as much as precision, together with the share of records where an identifier can still be read after redaction. A false alarm costs a masked word. A miss costs a leak. Both are in [`test-runs/benchmark.md`](test-runs/benchmark.md).

A detector pays for what it adds, in latency and in false alarms on look-alikes. Per 1,000 records on one 16 core CPU: rules 0.4 s, rules plus the statistical model 11 s, plus spaCy 24 s, plus GLiNER 87 s. GLiNER also flags many of the hard negatives (order numbers, commit hashes), so it is a recall tool and not a precision tool here.

## 3. The statistical model is trained on the generator, and the numbers say so

The statistical detector is trained on 1,500 generated records from a separate seed, using only four of the nine name cultures and only some of the templates. The benchmark corpus has all nine cultures and templates it never saw. Even so it shares the generator's way of writing, which is why its scores on the in-distribution corpus look excellent. A second benchmark, [`test-runs/benchmark_ood.md`](test-runs/benchmark_ood.md), uses three layouts the model never trained on (a quoted e-mail thread, meeting notes, a chat export). The ranking changes there, and a README that quoted only the first table would be misleading. Both are reported.

## 4. Cross document names: a threshold is a trade, so it is stated

Variants of one name (`Maria Santos`, `SANTOS, MARIA`, `MARIA SANTOS`, `María Santos`, `M. Santos`, `Maria S.`, one dropped letter) must land in one cluster, and a near twin (`Mario Santos`) must not. The resolver compares given and family parts with Jaro-Winkler similarity. A mention joins a cluster only when exactly one cluster qualifies. When two could own it, it joins neither: a wrong link joins two people's records, a missed link only costs a join. Mentions are clustered in a first pass, complete names before initials and bare names, because arrival order should not decide who a full name joins.

Over 300 generated people with 8 variants each and 30 near twins ([`test-runs/cross_document_names.json`](test-runs/cross_document_names.json)):

| threshold | variants in their person's main cluster | near twin pairs merged (of 30) | clusters merging different people |
|---|---|---|---|
| 0.90 | 90.3% | 24 | 45 |
| 0.93 | 89.5% | 11 | 32 |
| **0.96 (chosen)** | **80.9%** | **0** | **18** |
| 0.98 | 71.7% | 0 | 18 |

0.96 is the first threshold where no near twin merges. It costs about 9 points of recall against 0.90. Spanish double surnames and compound given names are where it loses recall, because "Silvia Pablo Fuentes" cannot be split into given and family by a rule.

## 5. k-anonymity: the price of k

Mondrian partitioning over zip, birth year and gender on 1,513 released rows, with an attacker who holds a named list of all 3,000 people. Source: [`test-runs/privacy.json`](test-runs/privacy.json).

| release | measured k | rows unique | information loss | rows re-identified | mean chance of guessing the right person |
|---|---|---|---|---|---|
| exact values | 1 | 61.3% | 0 | 722 (47.7%) | 66.4% |
| k = 2 | 2 | 0% | 1.4% | 0 | 29.0% |
| k = 5 | 5 | 0% | 4.6% | 0 | 8.8% |
| k = 10 | 10 | 0% | 7.7% | 0 | 4.1% |
| k = 25 | 25 | 0% | 21.2% | 0 | 1.5% |

k-anonymity bounds how confidently a row can be matched to a person using these three columns. It says nothing about the sensitive column (everyone in a group may share a diagnosis) and nothing about other columns an attacker might also hold. Information loss is the mean normalised certainty penalty over the three columns.

## 6. Differential privacy: epsilon is paid in error

A count has sensitivity 1, so Laplace noise of scale 1/epsilon makes it epsilon-differentially private, and the mean absolute error is 1/epsilon. Measured over 20,000 draws the error matches that to within 1.1% ([`test-runs/privacy.json`](test-runs/privacy.json)):

| epsilon | 0.01 | 0.1 | 0.5 | 1 | 2 | 5 | 10 |
|---|---|---|---|---|---|---|---|
| mean absolute error of a count (measured) | 101.1 | 9.9 | 2.01 | 1.00 | 0.50 | 0.20 | 0.10 |

The same noise, read as protection: an attacker who knows a person's quasi-identifiers and asks "was this person in the data" from a noisy cell count is right 100% of the time on the exact table, 52% at epsilon 0.1, 70% at epsilon 1 and 96% at epsilon 5 (chance is 50%). A small epsilon protects individuals and makes small counts useless. A count of 100 at epsilon 0.01 is wrong by about 100.

## 7. The structure aware pipeline: what it adds and what it costs

A field name or a column of mostly one type is used as a hint, and a short value under a hinted name is replaced whole unless a detector already covered it. A string that is itself JSON is opened. If any structured step raises, the plain text pass still runs, so the pipeline fails closed. Source: [`veilbench/structured.py`](../veilbench/structured.py), results in [`test-runs/robustness.json`](test-runs/robustness.json).

With the rules alone it cuts the records that still show an identifier from 137 to 107 of 192 JSON records and from 69 to 61 of 80 CSV records. With rules plus the statistical model both paths read 0 of 272 on this generated corpus, so the structure aware path buys nothing there and costs about 17 times the time (60 s against 3.4 s for the same records), because every leaf is a separate model call. Use it when the detector is weak or the schema is hostile, not by default.

## 8. The LLM second pass

See the section at the end of [`test-runs/benchmark.md`](test-runs/benchmark.md). It sees the text with everything already found replaced by `[X]`, so its tokens go on what is left. Its cost and latency are measured per call, and it only runs on a subset because the free key's daily and per minute token limits are shared with other work.
